Prologue: The Problem of Patch-Based Development

In the early 2000s, the Linux kernel development community faced a unique challenge. Thousands of developers contributed patches via email to mailing lists, where maintainers would review, request changes, and eventually merge them. Unlike modern pull request workflows, patches were iterative—often going through 10, 20, or even 30 revisions before acceptance.

Developers needed a way to maintain stacks of patches: organized series of changes that could be reordered, modified, and rebased while preserving their logical separation. Git, which Linus Torvalds released in April 2005, provided the foundation, but lacked native tooling for this workflow.

The Patch Stack Philosophy

A patch stack treats each logical change as an independent unit. Instead of one monolithic branch with mixed concerns, developers maintain discrete patches that can be individually modified, reordered, or dropped. This creates cleaner commit histories and easier code review.

Catalin Marinas, an ARM Linux kernel engineer, felt this pain acutely. Managing dozens of patches for ARM architecture support meant constant rebasing, careful tracking of what had been upstreamed, and painful merge conflicts. He needed tooling that understood patch stacks natively.

"With a patch stack workflow, multiple patches can be developed concurrently and efficiently, with each patch focused on a single concern, resulting in both a clean Git commit history and improved productivity." — StGit README

On July 10, 2005—just three months after Git's initial release—Catalin committed the first version of Stacked Git. The tool that would serve kernel developers for over two decades was born.

2005-2020 Era 1: The Python Foundation

The original StGit was a Python application of surprising sophistication. The initial commit (Release 0.4) shipped with 20 files totaling 2,871 lines of code, implementing the core operations that would define the tool: new, push, pop, refresh, and series.

Release 0.5: The Mailing List Revolution (August 2005)

Within a month, StGit gained the features that made it indispensable for kernel development. The mail command (b4bddc06) allowed developers to send patch series directly to mailing lists—a critical feature when email was the primary collaboration mechanism.

stg mail

Send patches via SMTP with proper threading and cover letters. Integrated maintainer aliases.

stg import

Import patches from files, mbox format, or URLs. Parse email headers to extract authorship.

stg pull

Integrate upstream changes while preserving the patch stack. Automatic rebasing.

stg clean

Remove empty patches after conflicts are resolved. Stack hygiene.

Kernel patches flow through email. How should StGit participate?

Chosen
Implement native stg mail with SMTP support, threading, and cover letters
Alternative

Release 0.6-0.7: Clone, Fold, Pick (September 2005)

The pace was relentless. September brought clone for initializing stacks in new repositories, fold for merging patches, id for showing patch hashes, and crucially, pick for cherry-picking patches between stacks.

Release 0.7 also restored the tutorial to the repository (d1c8fcd7)—a sign that adoption was growing and documentation mattered.

Release 0.8-0.9: Branch Management and UX (October 2005)

These releases focused on ergonomics. Branch cloning (cc3db2b1) allowed creating new stacks from existing ones. The show command displayed patch contents. Pager support (52f3900c) made reading diffs comfortable. And refresh --undo provided a safety net.

Release 0.10: The Testing Foundation (November 2005)

A pivotal release. Catalin copied Git's testsuite framework (aa9b1b9d), establishing automated testing that would protect the codebase through decades of changes.

How to ensure StGit quality and prevent regressions?

Chosen
Adopt git-core's proven test framework—shell-based tests that run actual stg commands

The goto command also appeared in 0.10 (994fdba7)—allowing direct navigation to any patch in the stack. Help output was classified by command category (5dc51fea), improving discoverability.

Era 1 Summary

In 15 years, Era 1 established StGit as the definitive patch stack tool. Starting from 2,871 lines of Python, it grew to a comprehensive system with 22 releases, supporting the Linux kernel's patch-email workflow. The architecture was stable, the test suite comprehensive, and the user base loyal.

But Python was showing its age. Startup time was noticeable. The codebase had accumulated technical debt. And a new maintainer was about to ask: what if we rewrote it in Rust?

2020-2022 Era 2: Python Maturation

Between 2020 and 2022, StGit underwent significant modernization while still in Python. This era saw the project professionalize its processes, reach v1.0 after 15 years, and prepare the foundation for what would become the Rust rewrite.

Release v0.23: Project Modernization (October 2020)

CONTRIBUTING.md was added (91cf6737), signaling a new focus on community growth. GitHub CI Actions replaced Travis CI (c2dfe597). Black formatting was applied (cb053a02). The Python codebase was being prepared for serious maintainership.

Era 2 Summary

Era 2 transformed StGit from a mature tool into a professionally maintained project. CI/CD, code formatting, contribution guidelines, and a proper version scheme brought StGit into the modern development era. But even as v1.5 shipped, the Rust rewrite was already underway.

2022 Era 3: The Rust Rewrite

In 2021, Peter Grayson began what would become StGit's most ambitious transformation: a complete rewrite from Python to Rust. The goal wasn't just language migration—it was to make StGit faster, safer, and more maintainable for the next 20 years.

Why Rust?

Python's startup overhead was noticeable when running many stg commands in scripts (see #145). Type safety was enforced only by discipline. Error handling was inconsistent. And the git2 library for Rust provided robust Git operations without shelling out to git commands.

How to rewrite StGit from Python to Rust?

Chosen
Incremental hybrid approach using pyo3. Rust commands coexist with Python during transition.
Not Chosen
Full Rust rewrite from scratch—too risky, would lose feature parity for extended period
Not Chosen
Continue with Python—would not address fundamental performance and safety concerns

Notable Issues During the Rewrite

#195 Libgit2 and Stacked Git do not support sparse checkouts
Upstream limitation in libgit2 (used via git2 crate). This would later motivate the switch to gitoxide.
#240 Short command forms like "stg ser" no longer work in 2.x
Clap's strict command matching broke muscle-memory abbreviations. Fixed with explicit alias support.
#235 How to update old branches with metadata version 4
Migration path needed for users with old stack metadata. Documented upgrade procedures.

Key Technical Decisions in the Rewrite

clap for CLI

Command-line parsing with clap. Type-safe argument handling. Automatic help generation.

git2 crate

Rust bindings to libgit2. Direct Git operations without shelling out. Faster and safer.

Zero unsafe

No unsafe blocks in the StGit codebase. Memory safety guaranteed by the compiler.

Typed Arguments

Patch names, ranges, and specifiers are now strongly typed. Compile-time correctness.

Era 3 Summary

The Rust rewrite was a triumph of incremental migration. By maintaining feature parity throughout and using a hybrid pyo3 approach, Peter Grayson delivered a complete language migration in under a year. The result: a faster, safer, more maintainable StGit ready for the next two decades.

2022-Present Era 4: Rust Maintenance & Evolution

With the Rust foundation in place, Era 4 has focused on refinement, new features, and keeping StGit current with the Rust ecosystem. In just 3 years, there have been 886 commits and 35 releases—more than all of Era 1.

Post-Rewrite Stabilization (v2.0.1 - v2.0.4)

The first months after v2.0.0 focused on catching edge cases and ensuring the Rust implementation matched Python's behavior exactly. Issues like #256: author set to gitoxide and #273: Windows errors drove rapid iteration.

v2.1.0: Configurable Conflict Policy (December 2022)

The first feature release post-rewrite. Configurable conflict resolution policies gave users control over how StGit handles merge conflicts during push operations. This addressed #212: stg rebase conflict handling.

Should StGit switch from git2 to gitoxide?

gitoxide is a pure-Rust Git implementation under active development.

Chosen in v2.2.0
Adopt gitoxide (054edb2c). Pure Rust dependencies, no C library overhead. Addressed #195 limitations.

v2.2.0: gitoxide Adoption (February 2023)

A significant architectural change. StGit migrated from git2 (Rust bindings to libgit2, a C library) to gitoxide (pure Rust Git implementation). This removed the last non-Rust dependency and improved build portability.

v2.3.0: Official Packages (Mid 2023)

Official deb, rpm, and msi packages published. Addressed #324: more .deb versions needed. StGit became installable on Debian, RedHat/Fedora derivatives, and Windows without building from source.

v2.4.0: After a 1-Year Gap (Late 2024)

After a longer development cycle, v2.4.0 brought accumulated improvements and dependency updates. Fixed #471: stg import --reject broken.

v2.5.0: New Year 2025 Release (January 2025)

New name subcommand for patch renaming (PR #513). stg rebase can now be called without arguments (PR #507). Commands organized by group in help output (PR #514).

v2.5.5: Current Latest (November 2025)

Squash improvements preserving consensus authors (#490). Continuous stgit.el Emacs mode updates (PR #536, PR #552, PR #573). gix (gitoxide) updated to 0.74.

The Two-Maintainer Model

What's remarkable about StGit's history is the continuity. Unlike many open-source projects that cycle through maintainers every few years, StGit has had essentially two maintainers in 21 years. This has resulted in:

  • Consistent vision: The patch stack philosophy remains unchanged from 2005
  • Stable API: Commands added in Era 1 still work identically in Era 4
  • Deep knowledge: Maintainers understand every corner of the codebase
  • Trust: The community knows who stands behind the tool

Conclusion: 21 Years and Counting

Stacked Git is a rare example of open-source longevity. Born from the practical needs of kernel development, it has evolved while staying true to its original purpose: making patch-based workflows manageable.
